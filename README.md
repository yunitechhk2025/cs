# Excel FAQ RAG 客服机器人

这是一个可直接落地的版本：把 Excel 常见问题库作为唯一知识源，先做检索，再用 AI 生成更自然的客服话术。

现已支持 **三种工作模式**，可在客服工作台中随时切换：

| 模式 | 说明 |
| --- | --- |
| 全AI (`auto`) | AI 自动检索题库并直接回复客户，无需人工介入（原有行为，默认模式） |
| 全人工 (`manual`) | 所有问题进入人工队列，由客服手动查看并回复，AI 不参与 |
| 人机协同 (`collab`) | AI 先生成建议回复（仅客服可见），客服审核/编辑后再发送给客户；若超时客服还没有发送回复，系统会自动把 AI 建议发给客户 |

客户网页 (`/`) 始终只显示一个聊天框；如命中全人工或协同模式，客户会看到“正在转接人工客服”的提示并自动轮询等待回复，无需手动刷新。

人机协同模式下，AI 建议生成后会启动一个倒计时（默认 **5 秒**，可在客服工作台的“工作台设置”中调整，1-300 秒）：如果这段时间内客服还没有点击「发送回复」，系统会自动把 AI 建议的回复发给客户，避免客户长时间等待；只要客服在倒计时结束前发送了回复（无论是直接采纳 AI 建议还是自己改写），就不会再自动发送。

### 知识库脱敏（本仓库为脱敏版）

题库（Excel）和产品说明文档都是直接沿用正式版的原始资料，里面写着真实品牌名和创始人姓名；而题库答案是**原文照搬**发给客户的（专业内容不经 AI 改写），所以在"加载知识库"这一层统一替换：`kb_desensitize.py` 里的 `REPLACEMENTS` 定义映射（`姜建华医生`→`yuni医生`、`澳洲肤润康`/`肤润康`/`FUYUNHON`→`YUNI` 等），`excel_rag_chatbot` 装载题库条目时和 `doc_rag_chatbot` 读取文档时各调一次。

- 替换按表中顺序执行，**长的规则必须在前**，否则"姜建华医生"会被短规则改成"建华"这种半截结果。
- 共用问题的判定（`_is_shared_question`）用替换**前**的原文，避免脱敏后跟 `_LEGACY_SHARED_QUESTIONS` 里的"是澳洲品牌？"对不上。
- 之所以不直接改 Excel/文档文件：原始资料保持与正式版一致，以后题库更新时直接替换文件即可，不用每次重新做一遍脱敏。

### 多产品支持

现已支持多个产品各自独立的题库（在 `web_app.py` 的 `PRODUCTS` 字典中配置）。客户在提问前需先在网页上选择要咨询的产品，选择结果会记录在浏览器本地并随每次提问一起提交；客服工作台的每条消息也会标注所属产品，方便区分处理。

**未命中题库的统一规则（任何模式下都适用）**：

- 若某个产品尚未配置 Excel 题库（`PRODUCTS` 中 `excel` 留空），该产品的所有提问都会被直接判定为"未命中"，不会消耗 AI 调用。
- 无论当前是全AI、全人工还是人机协同模式，只要题库检索未命中，系统都**不允许** AI 直接回复或编造答案，而是统一转人工处理（进入待处理队列）；只有确认命中题库时，全AI模式才会自动回复、协同模式才会生成 AI 建议并启动自动发送倒计时。
- **例外1**：单纯打招呼（"你好""在吗""hi"等、不带具体问题）不算未命中，任何模式下都会由 AI 直接回一句问候语，不转人工、不发邮件提醒；一旦打招呼的同时带了具体问题，仍会正常走题库检索流程。
- **例外2**：与产品咨询完全无关的闲聊/荒谬提问，或明显不构成真实客服需求的挑逗性/不当提问（"吃饭了嘛""这产品对国家安全有危害吗""哪里买到假货"之类；"哪里买到假货"特指字面上问"哪里能买到假货本身"，跟"怎么辨别真伪""在哪买正品才不会买到假货"这类正常防伪疑虑完全不同、后者仍会正常判定为相关；此外还包括内容本身低俗/色情/脏话骂人/人身攻击、明显违法违规、涉及政治敏感或国家安全违禁话题的提问，`_classify_irrelevant` 的 system prompt 里作为第 4 类单独列出）。这类说法千变万化，没法像打招呼一样靠关键词穷举，改用一次轻量 AI 判断：只有 AI **非常确信**完全无关/不构成真实需求时才直接回复引导语（第 4 类低俗/违法/涉政内容例外，只要命中就一律判定为无关，不会因为顺带提到产品就放过）；这类问题仍会完整落库（标记为 `matched=True`、`matched_question="无关闲聊/非常规提问"`，跟问候语的记录方式一致），方便管理员事后能在对话记录里查到，只是不进人工队列、不发邮件、不计入"转人工请求次数"统计；只要有一点点可能与产品相关，就判定为"相关"、正常走检索/转人工流程，避免真实问题被误判漏单。管理员可在工作台的「无关闲聊自动过滤」中随时关闭（对应 `skip_irrelevant_enabled` 设置，默认开启）。
  - **骂人/人身攻击内容的关键词兜底**：真实出现过"你是傻子"这种短句被 AI 误判成"命中题库、匹配度 100%"直接当正常问题回复的 bug（短文本语义检索容易凑巧跟无关的题库内容算出很高相似度，AI 语义判断对这种短句也不一定稳）。新增 `_is_abusive_language(text)`（正则匹配常见骂人词：傻子/笨蛋/蠢货/智障/脑残/白痴/废物等中英文粗话）和 `_is_irrelevant_question(question, product, model)`（先查关键词命中就直接判定无关，没命中再调 `_classify_irrelevant` 走 AI 语义判断）；`ask()` 和 `/transfer-question` 两处原来直接调 `_classify_irrelevant` 的地方都改成调 `_is_irrelevant_question`，保证骂人内容在进入题库检索之前就被拦下，不依赖 AI 调用是否成功。
### 置信度与 AI 自动回复阈值

每次题库命中都会计算一个**校准过的置信度**（0-100%，工作台「AI 识别」徽章上显示的就是它），由两部分加权融合（`excel_rag_chatbot.py`）：

- **AI 判断自评**（权重 0.6）：负责语义匹配的 AI 在返回匹配序号的同时自评一个 0-100 的把握值（90+ 几乎肯定 / 70-89 比较有把握 / 50-69 意图大致相同但表述含糊 / <50 勉强相关）。
- **检索证据**（权重 0.4）：关键词分（TF-IDF+字符重合，÷0.6 封顶）与语义分（embedding 余弦，0.35~0.75 线性映射到 0-1）各自校准到同一尺度后取较大值；该条目同时进入两路各自的 top-k 时再 +0.1。之所以不直接用原始检索分：两路检索的分数尺度完全不同（embedding 余弦对不相关文本也常有 0.2~0.35 的"高地板"），取 max 之后跨问题不可比，短文本还容易虚高（"你是傻子"曾被显示成 100% 就是这个原因）。原始检索分仍保留在 `AnswerResult.score` 里作诊断参考，工作台展示和决策一律用置信度。

**决策规则**：管理员可在「工作台设置 → AI 自动回复置信度阈值」调整（0-100，默认 **70**，设为 0 表示不启用、回到"命中即自动回复"）。题库命中后：

- **置信度 ≥ 阈值**：全AI模式直接回复客户；协同模式生成建议并启动自动发送倒计时（原有行为）。
- **置信度 < 阈值**：**不允许自动发送**。对话转人工进入待处理队列，AI 生成的回复保留为建议草稿——工作台标注"置信度未达阈值，不会自动发送"，回复框已预填草稿，客服确认或改写后手动发送；客户端表现与题库未命中一致（"正在为您转接人工客服"及后续留邮箱机制）。

几个边界情况：全人工模式的「题库检索标注」没有 AI 判断参与，显示的置信度只有检索证据部分；打招呼/无关闲聊仍按 1.0 记录（工作台用单独样式展示，不受阈值影响）；AI 语义匹配调用失败时的纯关键词兜底没有 AI 背书，置信度按检索证据打对折，通常达不到阈值、自然转人工。

- **例外3**：客户直接说"转人工""人工客服""找客服"等明确要求转接真人的话（不是一句需要检索/AI 判断的问题）。这类消息会在"无关闲聊"判断之前就被识别出来，跳过题库检索，直接进入转人工状态，不会先走一遍"AI 思考"的等待过程，也不会被无关闲聊过滤误判成"与产品无关"。因为"转人工"本身没有实际咨询内容，客户端会立即请客户补充一次具体问题（必填）+ 选填邮箱，详见下文"客户端等待提示"。
  - `/api/conversations/{id}/transfer-question` 接口对客户补充的这个具体问题，同样会调用 `_classify_irrelevant` 过一遍例外2那套判断（`skip_irrelevant_enabled` 开启时）——避免客户靠说一句"转人工"绕开题库检索这道过滤，把无关/低俗/违法/涉政内容硬推给人工客服。命中的话直接 `database.mark_answered(...)` 写入无关闲聊的引导语并返回 `{"success": true, "irrelevant": true, "answer": "..."}`，不再执行邮箱保存/邮件通知/`conversation_updated` 广播；前端 `renderTransferQuestionPrompt` 收到 `irrelevant: true` 后只展示这句引导语（`addMessage(data.answer, "bot")`）就直接 `return`，不展示邮箱气泡、不调用 `pollAnswer`，整个转人工流程到此终止。

### 转人工邮件提醒

一条提问进入人工队列时（题库未命中，或全人工模式下的任意问题），系统**不会**立即发邮件，只会把这条对话实时广播给客服工作台。邮件通知只有一个触发条件：**客户在等待过程中主动留下了合法格式的邮箱**（对应"留邮箱"或"补充问题+选填邮箱"这两个入口），此时才会真正发一封邮件通知客服/管理员，内容包含**客户（访客编号，跟工作台会话列表看到的编号一致）**、产品、模式、客户提问、客户邮箱、对话编号；客户不填邮箱则完全不会触发邮件。

- **全人工模式例外**：即使客户在该模式下留了邮箱，也**不会**发邮件——该模式下客服本就要一直盯着工作台处理每条对话，不需要邮件提醒；客户留的邮箱依然会保存、在工作台可见，方便客服直接联系，只是不触发邮件这个动作。

邮件通过标准 SMTP 发送，配置方式有两种，**后台配置优先于 `.env`**：

- **推荐：登录客服工作台配置**（「工作台设置 → SMTP 发信配置」）：管理员可以直接在页面上填发信服务器、端口、账号、密码、发信人、TLS/SSL，保存后立即生效，还能点「发送测试邮件」当场验证配置对不对，不需要 SSH 登录服务器、也不需要重启容器。密码字段留空保存表示不修改已保存的密码。配置存在数据库里（`data/qa.db`，已通过 Docker volume 持久化），换服务器部署也不会丢。
- **兜底：`.env` 里的 `SMTP_*` 变量**（见 `.env.example`）：后台还没配置过时（数据库里没有 `smtp_host`）会自动回退到这些环境变量；两者都没配置时会跳过发送并只打印警告日志，不影响客户提问、客服回复等主流程。

收件邮箱同理：默认取 `.env` 里的 `NOTIFY_EMAIL_TO`，管理员也可以在「工作台设置 → 邮件提醒收件人」里直接修改（支持逗号分隔多个收件人），后台配置优先、改动立即生效。

管理员还可以在客服工作台的「工作台设置」中额外开启**待处理队列定时提醒**：只要队列不为空，就按设定的分钟数（1-1440）周期性发一封汇总邮件，告知当前有多少位客户、多少条问题待处理，邮件里列出的每一条问题也会标注是哪个访客提出的；这个定时提醒与上面的即时提醒是两套独立机制，互不影响。

### 每日数据日报

管理员可在「工作台设置 → 每日数据日报」中开启/关闭，并设置每天的推送时间点（默认 **09:00，按香港时间计算**）。开启后，每天到点会自动发一封邮件，汇总**前一个香港日历日（00:00-24:00）**的数据：

- 咨询用户数（按客户去重）
- 总对话条数
- 转人工请求次数（口径：全人工模式下的任意问题，或全AI/协同模式下题库未命中——与是否实际发出邮件提醒无关）

发送渠道、收件邮箱复用上面的 SMTP 配置和邮件提醒收件人设置，不需要额外配置。

### 客户端等待提示

客户提问转人工后，网页先显示"已收到您的问题，正在为您转接人工客服，请稍候"，这条消息会**一直保留在对话记录里，不会被后续提示覆盖或删除**。

- **题库未命中（全AI / 协同模式）**：如果客服在 **10 秒**内还没有回复，会在这条消息**下方新增一条**消息，提示"人工客服正忙，留下您的邮箱，客服稍后通过邮箱回复您"，并就地提供邮箱输入框（对应后端 `/api/conversations/{id}/leave-email`）；客服最终的回复会写入这条新消息里。
- **全人工模式的任意问题**：**完全没有**上面这套"留邮箱"提示——问题已经直接进了工作台待处理队列，客服本就要一直盯着处理，客户端只会安静持续轮询，10 秒后不会弹出任何额外提示；客服最终在工作台回复后，答案会**另起一条新消息**展示，不会覆盖或替换掉"已收到您的问题…"这条记录。

如果客户是直接说"转人工"之类明确要求转接真人（见上面例外3），后端 `/api/ask` 会返回 `need_transfer_details: true`，客户端不需要等 10 秒、也不演"AI 思考"这段过程，立即展示**想咨询的问题**输入框（必填，提交后会替换掉数据库里"转人工"这句占位提问）（对应 `/api/conversations/{id}/transfer-question`）；若当前工作模式不是全人工模式，还会额外提供**邮箱**输入框（选填）——**全人工模式下不会展示这个邮箱输入框**，因为该模式完全不需要留邮箱这套机制。此时客户端还**不会**开始轮询（避免跟提交后另起的轮询互相冲突改同一条消息），要等客户真正提交这个表单之后才开始。

提交后，客户填的问题、邮箱（如果填了）都各自单独 `addMessage` 成一条正常大小的消息保留在对话记录里，不再是挤在提示语下面的一行 `.email-capture-status` 小字（那个小字样式现在只用来显示格式校验失败之类的即时错误提示）。紧接着新增一条 bot 消息作为轮询目标，文案按是否填了邮箱分两种：

- **没填邮箱**：显示「已将您的问题「XXX」更新给人工客服，请稍候」（`XXX` 是客户刚提交的具体问题），并以 `emailProvided: false` 调 `pollAnswer(conversationId, el, matched, mode, { question, emailProvided })`，跟题库未命中场景完全一样——等超过 10 秒客服还没回复，会在下面新增"人工客服正忙，留邮箱"提示，让客户这时候补填邮箱（提交成功后的确认文案同样带上客户具体问的内容和刚填的具体邮箱）。
- **填了邮箱**：**立即**显示「已将您的问题「XXX」更新给人工客服，请耐心等待客服回复您～」（带上客户具体问的内容），并以 `emailProvided: true`、`email: <客户填的邮箱>` 调 `pollAnswer`；如果客服在 10 秒内就回复了，直接替换掉这条确认消息；如果超过 10 秒仍未回复，会在下面**新增一条**静态确认消息「人工客服正忙，已邮件通知客服，请耐心等待客服通过邮箱【XXX@XXX.XXX】回复您～」（带上客户具体留的邮箱地址，不会再弹一次输入框追问邮箱，也不会重复"已将您的问题…更新给人工客服"这句已经说过的话）。所有"客服会通过邮箱回复"类的确认文案，邮箱地址都统一用「通过邮箱【具体地址】回复您」这种带书名号的格式，方便客户一眼认出哪部分是自己的邮箱。

**留完邮箱后照常走 20 秒闲置提示**：客户已经留了邮箱、接下来只等客服发邮件回复时，这轮等待可能长达几小时，不能一直压着闲置计时（`scheduleIdleEndPrompt` 在 `activeWaits > 0` 时不启动），否则那句"是否结束本次对话"永远不会出现。所以确认文案一出现（`emailProvided=true` 时是 10 秒后的"已邮件通知客服"提示；客户在 `renderLeaveEmailPrompt` 表单里补填邮箱时是提交成功的那一刻，通过气泡上的 `_onEmailLeft` 回调通知发起轮询的一方），`pollAnswer` 就调 `releaseWaitForEmailReply()` 把这轮等待从 `activeWaits` 里摘掉，闲置 20 秒后照常提示结束对话。轮询本身继续在后台进行，客服若直接在工作台回复，答案照样写进对应气泡（此时不再重复 `endWait()`，只重新起一次闲置计时）。

`pollAnswer` 的 `options.question` 参数用来在"已将您的问题「XXX」更新给人工客服…"类确认文案里回显客户具体问的内容；`options.email` 用来在 10 秒后的确认文案里回显客户具体留的邮箱地址；`options.emailProvided` 决定 10 秒后到底是弹交互式的"留邮箱"输入框（`renderLeaveEmailPrompt`），还是直接换成一条带具体邮箱的静态确认消息。刷新页面恢复历史记录时（`restoreHistory`），后端 `/api/conversations/by-session/{session_id}` 会把客户自己留的邮箱原文一并返回（字段 `email`），确保刷新后这些确认文案里的邮箱地址依然能正确回显。

邮箱这一部分（题库未命中场景 / 非全人工模式下的补充问题场景）的规则都一样：后端先校验是否为**真实格式的邮箱**（形如 `xxx@xxx.xxx`，不是随便打几个字符），格式不对会提示错误并拒绝提交；只有格式合法才会真正落库并发一封邮件通知客服（内容含访客编号、客户提问、客户邮箱、对话编号），方便客服直接通过邮件回复。**转人工要真正通知客服，必须客户填写合法格式的邮箱**——客户如果不填邮箱，则不会触发这条邮件通知，但客服仍能在工作台的待处理队列里实时看到这条对话（问题内容的更新与邮箱是否填写无关，不填邮箱同样会更新问题内容）。**全人工模式下完全没有留邮箱这套机制**（无论是普通提问还是主动说"转人工"），客户端不会展示任何邮箱输入框，也不会有对应的邮件通知，因为该模式客服本就要一直盯着工作台。客户提交成功后，输入框位置会清空、由上面那条新增的 bot 消息承接后续状态。整个过程网页仍会在后台持续轮询（`pollAnswer` 不再设置最大轮询次数/超时兜底文案），一旦客服真正在网页端回复，答案会自动展示出来、无需客户手动刷新——AI 反馈不会超过 10 秒这个量级，涉及转人工的场景在 10 秒时已经进入上面的留邮箱/补充问题机制（全人工模式则是直接安静轮询），所以不需要再额外设置一个"等 10 分钟后放弃"的兜底提示。全人工模式下，客服的回复**永远另起一条新消息**展示，绝不会覆盖"已收到您的问题，正在为您转接人工客服，请稍候"这条记录；非全人工模式下如果客服在 10 秒内就回复了（还没弹出"留邮箱"提示或确认消息），回复会直接替换掉这条等待提示（相当于把"请稍候"自然过渡成真正的答案）。

### 客户端会话标识 / 刷新恢复聊天记录

`static/index.html` 用 `sessionStorage`（不是 `localStorage`）保存客户浏览器的会话标识 `fuyunhon_session_id`——`sessionStorage` 的生命周期跟"标签页"绑定：刷新页面（F5）不会清空，关闭标签页/浏览器窗口才会清空。借着这个特性：

- **刷新页面**：`sessionStorage` 里的会话 id 还在，页面加载时按下述"逐条重放"机制恢复出跟刷新前完全一致的聊天记录。
- **关闭标签页/浏览器**：`sessionStorage` 被清空，下次打开是全新的会话 id，不会带着之前的聊天记录，工作台里也会被当成一个新的"访客编号"（`database.list_sessions` 按 `session_id` 首次提问时间分配编号）。

**刷新恢复 = 聊天记录逐条重放（治本机制）**：早期版本的刷新恢复靠 `conversations` 表每条对话的"最终状态"去推演出一份近似的聊天记录，为此陆续打过多个补丁（`awaiting_transfer_details` 记住未提交的转人工表单、`created_at`/`elapsedMs` 续算 10 秒倒计时、`addMessageAfter` 保持提示插入顺序、补画邮箱气泡、`is_explicit_transfer` 区分主动/被动转人工话术），但转人工这类多步流程的过程性消息（引导语、第一次确认、"人工客服正忙"原始提示等）在推演中天然丢失或措辞对不上，刷新后看起来像"换了一个界面"。现在改为逐条落库、逐条重放：

- **落库**：新增 `chat_messages` 明细表（`database.py`），客户端每显示一条消息气泡就调 `POST /api/chat-messages` 记一行，DOM 里的每个气泡对应明细表里的一行；等待类气泡"先占位、后原地更新"（"AI 正在思考…"最终被答案替换时，通过 `POST /api/chat-messages/{id}/update` 原地更新同一行）。`sort_key`（REAL）是排序键：`addMessageAfter` 插入的延迟提示带 `after_id`，服务端取前后两条消息 sort_key 的中间值，保证明细顺序跟 DOM 顺序一致。落库请求在前端通过一个串行 Promise 队列（`recordQueue`）按显示顺序依次发出；单条失败静默忽略，只影响那一条的恢复。
- **气泡类型（kind）**：`text`（普通文字）/ `waiting`（等待中，同时是这条对话的轮询锚点）/ `transfer_form`（"请描述您的问题"表单）/ `email_form`（"人工客服正忙，留邮箱"表单）/ `busy_note`（已留邮箱场景下的"客服正忙，已邮件通知"提示）/ `image`（客户发送的图片，`content` 存图片 URL）/ `idle_prompt`（闲置 20 秒后的"是否结束对话"提示，带「继续咨询 / 结束对话」按钮）/ `session_end`（会话已结束）。后端 `web_app.py` 的 `CHAT_MESSAGE_KINDS` 是这份类型的白名单，新增类型必须同步加进去，否则落库时会被降级成 `text`、刷新后还原不出原样。
- **重放**（`replayChatMessages`）：`GET /api/chat-messages/by-session/{session_id}` 拉明细 + `GET /api/conversations/by-session/{session_id}` 拉对话状态，按顺序逐条渲染。只有两类气泡会复活成可交互状态：① 还没提交的表单（`transfer_form` 且 `awaiting_transfer_details=1`、`email_form` 且未留邮箱未回复）重新渲染成表单；② 还没等到回复的 `waiting` 气泡接回 `pollAnswer`（`elapsedMs` 按真实提问时间续算；明细里已有 `busy_note`/`email_form` 时传 `skipBusy: true` 不再重复补提示；复活的邮箱表单作为 `followUpEl` 传入，最终答案照旧写进那个气泡）。其余一律按静态文字原样展示，重放期间 `recordingEnabled=false`，不会把恢复出来的气泡再记一遍。
- **老会话兜底**：明细表为空（逐条落库功能上线前就开始的会话）时退回旧的推演式恢复（`restoreHistoryFromConversations`），推演产生的气泡照常落库，之后再刷新就走逐条重放。
- **已结束的会话刷新即重新开始**：结束语说的是"刷新页面即可重新开始"，所以已结束的会话不走上面的重放。客户点「结束对话」时除了落一条 `session_end` 明细，还会往 `sessionStorage` 写一个 `fuyunhon_session_ended` 标记；下次加载页面时同步读到这个标记就清掉它和 `fuyunhon_session_id`，从空白开始一个全新会话（旧记录仍完整留在库里，工作台照样看得到，只是会算成一个新的访客编号）。用本地标记而不是等历史记录拉回来判断，是为了不受接口失败影响；结束时间早于这个标记上线的老会话，则在 `restoreHistory` 里发现明细中有 `session_end` 时同样丢弃旧会话、不重放。**没结束的会话刷新后界面照旧**，仍按逐条重放原样恢复。

无关闲聊/荒谬提问（`_classify_irrelevant` 命中的情况）也会完整落库、正常返回真实的 `conversation_id`，因此刷新页面时同样会出现在恢复的历史记录里，跟其他正常问答一样。

### 客户端发送图片 + 视觉模型识别

输入框内左侧有一个加号按钮，客户点击后唤起系统文件选择框（手机上即相册/拍照），可以把患处照片、包装照片等直接发给客服。

**选中图片不会立刻发出**：图片先以缩略图形式挂在输入框上方（可点 × 撤掉），客户接着把想问的话打完，点「发送」时图片和文字**一起**送出——先上传图片（服务端同步做视觉识别并暂存描述），再把文字问题发给 `/api/ask`，于是这次提问天然就带上了图片描述。这样"发图 + 说明想问什么"是一次完整的表达，而不是两条各自孤立的消息。只挂了图片、一个字都没打时也允许发送，此时走下面的"只发图不说话"逻辑。

- **上传**：`POST /api/upload-image`（`multipart/form-data`，带 `session_id`），限 jpg / png / gif / webp、单张不超过 5MB，超限或格式不对返回 400 并在聊天里提示客户。图片存到 `data/uploads/`（与数据库同一个 Docker volume，重启/重新部署不丢），文件名统一用随机 32 位 hex + 原扩展名，原始文件名不落盘。
- **读取**：`GET /uploads/{filename}`，文件名必须完全匹配"32 位 hex + 允许的扩展名"这个生成规则，不匹配一律 404，因此不存在路径穿越。
- **展示与恢复**：上传成功后客户端插入一条 `kind=image` 的气泡（缩略图，点击在新标签页看原图）并照常落库，刷新页面时按明细原样重放。
- 依赖：文件上传需要 `python-multipart`（已加入 `requirements.txt`）。

**图片 → 文字描述 → 并进提问**：上传成功后服务端立刻调视觉模型（`VISION_MODEL`，默认 `qwen3-vl-flash`）把图片内容转成一段**客观**的文字描述（system prompt 明确禁止医学判断、禁止用药建议，只描述看得见的事实，100 字以内），存入 `pending_images` 表暂存。

- **图片与提问一起发送（常规路径）**：`/api/ask` 会取出该会话尚未被用掉的图片描述，合成 `客户原话 + \n【客户同时发来图片，图片内容】描述` 作为检索/回答用的问题，走**完全相同**的题库检索、命中判定、三种模式逻辑——AI 依然只能照题库回答，未命中一律转人工，视觉模型只负责"把图看懂成文字"，不参与作答。取出后即标记 `consumed`，避免同一张图被并进之后每一个问题里把检索带偏。
- **合并窗口**：`PENDING_IMAGE_MAX_AGE_SECONDS`（10 分钟）。之所以不是 10 秒，是因为客户只发图不说话时机器人会在 10 秒后主动追问，客户回答这句追问时图片必须还有效。
- **客户只发图不说话**：客户端在发图 10 秒后主动补一句「已收到您的图片～请问您想咨询关于这张图片的什么问题呢？」（插在那张图片下面）；客户在这 10 秒内自己发了问题就取消追问。客户回答这句追问时，图片描述仍在合并窗口内，照样会并进那次提问。
- **附带图片时的两个例外**：跳过"无关闲聊自动过滤"（"这个正常吗"这类只看文字很容易被误判成与产品无关），也跳过"纯打招呼"捷径（发了图再说"你好"，真正要问的是图片）。客户明确说"转人工"仍照常转接。
- **识别失败不影响主流程**：没配 `OPENAI_API_KEY`、模型不支持图片、超时等情况下描述为空字符串，图片照常发送成功、客服照常能看图，只是这次提问不带图片描述。
- **客服工作台**：图片本身不产生 `conversations` 记录，`GET /api/agent/sessions/{session_id}` 会把图片按时间插进该会话的问答流里（`item_type=image`），并带上 AI 识别描述；附带了图片的那条提问也会显示「📷 本次提问附带客户图片，AI 识别：…」，客服可以核对 AI 到底"看见了什么"。因为会话列表仍由 `conversations` 分组而来，如果客户只发了图、还没提过任何问题，该会话要等他发出第一条文字提问后才会出现在列表里。

### WhatsApp 接入（WhatsApp Cloud API）

客户可以直接在 WhatsApp 里咨询，答案与网页端完全一致：webhook 收到消息后调的是**同一个** `_process_question()`（`/api/ask` 也只是它的一层薄封装），题库检索、命中判定、无关内容过滤、三种工作模式的行为一模一样，改一处两个渠道同时生效。没配 WhatsApp 相关环境变量时，webhook 拒绝所有请求，其余功能完全不受影响。

- **接口**：`GET /api/whatsapp/webhook` 是 Meta 的握手校验（比对 `hub.verify_token` 后把 `hub.challenge` 以**纯文本**原样返回，返回 JSON 会验证失败，这是最常见的坑）；`POST /api/whatsapp/webhook` 接收消息事件。`GET /api/whatsapp/status`（需管理员登录）用来自查各项配置是否就绪，不返回任何密钥内容。
- **安全**：每个 POST 都校验 `X-Hub-Signature-256`（用 app secret 做 HMAC-SHA256）。未配置 `WHATSAPP_APP_SECRET` 时跳过校验并打警告，方便刚接通时先跑流程，正式对外前必须配上——webhook 地址是公网可访问的。
- **20 秒应答**：Meta 要求 20 秒内返回 200，否则判定失败并不断重推。识别图片、调 AI 远超这个时间，所以端点只做校验和解析，处理丢进 `BackgroundTasks`。重推的 message id 与首次相同，`whatsapp_processed_messages` 表按 message id 去重，避免同一句话被回答两遍。
- **会话映射**：一个手机号就是一个客户，`session_id` 固定为 `wa:<手机号>`。工作台按 `session_id` 分组的逻辑因此完全不用改，WhatsApp 客户就是一个普通访客（`client_ip` 列显示成 `WhatsApp <手机号>`，一眼能看出渠道）。与网页端不同的是，WhatsApp 会话不会因为"关掉标签页"而重置，客户几天后再来，客服看到的是完整历史。
- **产品选择**：用 Meta 的交互式按钮（`whatsapp_contacts.product` 记住选择，按钮标题上限 20 字符）。客户没选产品就先发了问题时，那句话会暂存在 `pending_question`，点完按钮立刻按它作答，不用让客户重打一遍。客户说"切换产品/换产品/重新选择"等关键词会重新弹出按钮。
- **图片**：webhook 给的是 media id，需要两步下载（先换 5 分钟有效的临时地址，再带令牌取内容），存进和网页端同一个 `data/uploads/`，走同一个视觉模型识别成描述后存入 `pending_images`——之后的提问会自动合并（逻辑与网页端共用）。图片自带 caption 时等于"图 + 问题"一起发来，直接按 caption 作答；只发图不说话则回一句追问。
- **转人工**：客户说"转人工"这类没有实际内容的话时，记下这条对话（`awaiting_transfer_conversation_id`），客户下一句话补进**同一条**对话里，避免队列里留下一条只写着"转人工"的空对话；这句补充的问题同样要过一遍无关内容判断，否则客户可以靠一句"转人工"绕开拦截。网页端那套"留邮箱等邮件回复"在 WhatsApp 上不需要——客服直接回 WhatsApp 即可。
- **客服回复要"推"出去**：网页端客户是自己轮询把答案拉回去的，WhatsApp 没有这个机制，所以 `agent_answer()` 和协同模式的 `_auto_send_after_timeout()` 在标记已回复后都会调 `_push_answer_to_whatsapp()`。**注意 Meta 的 24 小时客服窗口**：客户最后一条消息之后超过 24 小时，普通文本会被拒收，只能改用审批过的模板消息（当前未实现，发送失败会把 Meta 的原始报错打进日志）。
- **代码位置**：`whatsapp.py` 只封装"跟 Meta 打交道"这一层（发消息、下载媒体、校验签名、长文本拆分），业务流程都在 `web_app.py` 的 `_handle_whatsapp_*` 系列函数里，以后要换成 BSP（Twilio、360dialog 等）只需要替换 `whatsapp.py`。

### 客服工作台：回复框显示规则 / 草稿保存

回复框（`compose-area`）只在对话真正需要客服手动处理时才会渲染：题库未命中、全人工模式的任意问题、或客户主动要求转人工，这三种情况会显示；全AI模式已直接回复、或人机协同模式题库命中且 AI 已生成建议（进入自动发送倒计时）这两种情况**不会**显示回复框，因为这类对话不需要人工介入（AI 已经处理完，或即将自动发送）。

回复框只有一个「发送回复」按钮，客服可以随时直接输入内容并发送给客户；发送成功后对话变为"已回复"状态，回复框自动消失。（曾经有一套"认领此问题 / 释放认领"的多客服协作机制，只有多个客服同时在线可能抢同一个对话时才有意义，已去掉，`/api/agent/claim`、`/api/agent/release` 这两个接口以及对应的 `claimed` 对话状态不再产生新数据，`database.py` 里仍保留 `claimed_by` 字段和对 `'claimed'` 历史状态值的兼容处理，避免影响旧数据。）

由于工作台会定期（WebSocket 推送 + 5 秒兜底轮询）刷新整个消息列表，`static/agent.html` 用一个按对话 id 索引的 `composeDrafts` 内存对象缓存客服正在输入但还没发送的草稿：`textarea` 的 `input` 事件把内容写入草稿箱，重新渲染时优先读草稿箱、而不是每次都用 AI 建议覆盖，避免客服打字打到一半被刷新清空；发送成功或对话变为已回复后清除对应草稿。

草稿箱只能保住"已经敲下确认的字"，保不住中文输入法里还没上屏的拼音候选词——那部分状态是绑定在具体的 `textarea` DOM 节点上的，如果这时候整段重渲染（`renderThread` 每次都会 `innerHTML` 整个替换掉消息列表），候选词所在的节点被销毁重建，候选词就直接丢了。所以 `renderThread()` 开头会判断 `document.activeElement` 是不是当前正聚焦在某个 `[data-answer-input]` 输入框上，如果是就直接跳过这次渲染（不触碰 DOM）；`textarea` 的 `blur` 事件会补触发一次 `renderThread()`，把输入期间攒下的更新追平。

## 4) 客服工作台

访问：

```text
http://127.0.0.1:8001/agent
```

用 `.env` 中配置的管理员账号登录（默认 `admin` / 见 `ADMIN_PASSWORD`）。

- **右上角模式快捷切换**（仅管理员可点击）：点击即可在全AI / 全人工 / 人机协同之间切换，立即生效，无需重启服务；非管理员只会看到当前模式的只读提示。
- **工作台设置**（右上角按钮，弹出面板）：管理员可在此配置 SMTP 发信服务器（含一键测试发送）、邮件提醒收件人、调整人机协同的自动发送超时时间、设置 AI 自动回复置信度阈值（低于阈值转人工，见上文"置信度与 AI 自动回复阈值"）、开启/关闭待处理队列定时提醒邮件并设置提醒间隔（分钟）、开启/关闭每日数据日报并设置推送时间点（香港时间），以及管理客服账号。
- **待处理队列**：全人工/协同模式下的新问题会实时推送到所有在线客服（WebSocket + 5 秒兜底轮询），支持多人同时在线。
  - 协同模式下，队列条目会显示 AI 生成的建议回复（含匹配度），客服可直接采纳或编辑后发送。
  - 回复框只有一个「发送回复」按钮，任意在线客服都可以直接输入内容并发送，不需要先"认领"。
- **会话列表搜索 + 未处理红点**：会话列表顶部有一个搜索框，客户没有真实姓名，所以按"访客编号"匹配（输入 `13` 或 `访客13` 均可），跟"全部/待处理/已回复"筛选可以同时生效（`static/agent.html` 里的 `matchesSearch()`）；每个客户头像右上角，只要该客户还有 `pending_count > 0` 的未处理问题，就会显示一个红色小圆点（`.unread-dot`），客服扫一眼列表就能看出哪些客户还没处理完，不需要逐条点开确认。
  - 会话列表每一行不再显示"产品"徽章：因为徽章之前取的是 `session.last_product`（该客户最后一条消息咨询的产品），而同一个客户完全可能先后咨询过多个不同产品，只显示最后一个会误导客服。产品信息仍保留在点开会话后每条具体消息自己的徽章上（`item.product`，每条消息各自记录当时提问的产品，不会混淆）。
  - 头像颜色不再随"待处理/已回复"状态变化（原来待处理是橙色渐变、已回复是绿色渐变），统一改成一个素色（`#9aa5ba`），因为该状态已经由旁边的文字徽章和未处理红点表示，颜色再变化属于重复信息、还容易显得杂乱。
- **修复"打招呼/无关闲聊"被工作台误显示成"命中相关资料 100%"**：后端为了统计口径，把"打招呼"和"无关闲聊/低俗违规内容"这两类跟真实题库命中一样存成 `matched=1、match_score=1.0`，但 `matched_question` 实际是 `"问候语"` / `"无关闲聊/非常规提问"` 这两个固定占位字符串，不是真的题库问题。`static/agent.html` 的 `renderIntentBlock()` 之前没区分这两种"伪命中"和真实命中，导致像"吃了吗"这类无关闲聊被展示成自相矛盾的"命中相关资料（匹配度100%）"。现在新增 `SKIP_LABELS` 映射，`matched_question` 命中这两个占位字符串时改用单独的"💬 日常问候，已自动回复"/"🚫 无关闲聊/非常规内容，已自动过滤"样式（`.intent-badge.skip`），不再展示假的匹配度和假的"题库问题"。
- **历史记录**：展示最近 50 条问题（覆盖全AI、全人工、人机协同三种模式），每条都会标注「题库检索标注」——命中了题库中的哪个问题及对应答案，或提示未命中，方便复核 AI 是否按题库准确回复。
- **客服账号管理**（仅管理员）：可在工作台内直接创建新的客服/管理员账号。

> 建议登录后立即修改默认管理员密码：可调用 `POST /api/agent/change-password`（`{"old_password":"...","new_password":"..."}`，需携带登录返回的 `token`）。

## 6) 参数说明

**回答机制**：每次提问分别用关键词检索（TF-IDF）和语义向量检索（embedding 余弦相似度）
各取 `top-k` 条候选，取并集后交给 AI 在候选中做语义判断——即使客户的措辞、语序、同义/口语化
表达（例如"涨豆豆"对应"长痘"）与题库原文不同，只要意图相同即可命中；语义检索弥补了纯关键词
检索对这类改写问句召回不足的问题。命中后，AI 只生成一句开场白/过渡语，专业内容（成分、功效、
用法用量、禁忌等）始终是题库答案原文的直接拼接，不经过 AI 改写，确保逐字一致。如果 AI 判断
所有候选都不匹配，或调用失败兜底走关键词分数判断，会返回引导客户补充关键词的话术。每次提问的
检索结果（命中的题库问题/答案，或未命中）都会记录在后台，客服工作台的问题卡片上会显示
「题库检索标注」供人工核对。首次启动时会调用一次 embedding 接口为所有题库问题建立语义索引，
如果该接口调用失败（无网络/无 API Key），会自动降级为纯关键词检索，不影响其余功能。

- `--top-k 3`：每次返回的知识条数，默认 3
- `--min-score 0.1`：最低命中阈值，太低就会拒答并引导补充问题
- `--self-test`：跑一次样例问答后退出，便于快速验收

网页版本也支持这些环境变量：

- `FAQ_EXCEL_PATH`：Excel 路径，默认读取当前目录的肤润康题库
- `FAQ_TOP_K`：关键词检索和语义检索各自的候选条数（取并集后交给 AI 做语义匹配），默认 8
- `FAQ_MIN_SCORE`：AI 语义匹配调用失败时，兜底关键词检索所用的最低命中阈值，默认 0.1
- `FAQ_EMBED_MODEL`：语义检索所用的 embedding 模型，默认 `text-embedding-v3`
- `OPENAI_MODEL`：模型名，默认 `qwen3.6-flash`
- `OPENAI_BASE_URL`：默认 `https://dashscope-intl.aliyuncs.com/compatible-mode/v1`
- `VISION_MODEL`：把客户发来的图片转成文字描述所用的视觉模型，默认 `qwen3-vl-flash`。阿里百炼可选（单价为每百万 token 输入/输出）：`qwen3-vl-flash`（0.15/1.5，专用视觉模型里最便宜，做"描述图片"够用）、`qwen3-vl-plus`（1/10，视觉理解更强）、`qwen3.6-flash`（1.2/7.2，就是 `OPENAI_MODEL` 默认在用的模型，本身支持图像，不想多配一个模型时用它）、`qwen3.7-plus`（2/8，旗舰，效果最好成本最高）。价格与可用地域以[阿里云百炼模型价格](https://help.aliyun.com/zh/model-studio/model-pricing)为准

## 7) GitHub 自动部署到阿里云 ECS（脱敏版，与正式版同机）

本仓库是**脱敏演示版**，可与正式版（`fuyunhon_cs`，通常占 `8000`）部署在同一台 ECS 上，互不覆盖：

| | 正式版 | 脱敏版（本仓库） |
| --- | --- | --- |
| 仓库 | `yunitechhk2025/fuyunhon_cs` | `yunitechhk2025/cs` |
| 服务器目录 | `~/fuyunhon_cs` | `~/cs` |
| 容器名 | `fuyunhon-faq-chatbot` | `cs-demo-chatbot` |
| 对外端口 | `8000` | `8001`（`.env` 里 `APP_PORT`） |
| 访问地址 | `http://IP:8000` | `http://IP:8001` |

仓库包含两个 Actions 工作流（**密钥不走 SSH envs/base64/scp**，避免传参失败）：

| 工作流 | 何时用 |
| --- | --- |
| **Bootstrap server .env**（手动） | 首次、或要更换 API Key 时跑一次，写入服务器 `~/cs/.env` |
| **Deploy to Aliyun ECS**（push `main` / 手动） | 日常发版：只拉代码 + `docker compose up` |

在 GitHub → Settings → Secrets and variables → Actions → **Repository secrets** 添加：

- `ECS_HOST` / `ECS_USER` / `ECS_PASSWORD`：SSH
- `DASHSCOPE_API_KEY`：模型 API Key（Bootstrap 时写入 `.env` 的 `OPENAI_API_KEY`）

同时在云安全组放行 **8001**。

**首次上线顺序：**

1. Actions → **Bootstrap server .env** → Run workflow  
2. Actions → **Deploy to Aliyun ECS** → Run workflow  
3. 打开 `http://IP:8001` ；工作台 `http://IP:8001/agent`（默认 `admin` / `changeme`）

之后改代码 push 到 `main` 只会走 Deploy，不会反复折腾传密钥。

> `.env` 只存在于服务器、不进 git。脱敏版与正式版必须目录/容器名/端口分离，避免串数据和抢端口。
